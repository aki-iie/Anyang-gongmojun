# 문진 질문 재검토 — 카드 비교와 계단 개수

작성 2026-09-17 · 근거 `field_survey_chunghun34.csv` (충훈동 34가구 실측) · `scripts/diagnose.py`

이 문서는 **가중치와 무관하다.** 지금 이 서비스에는 가중치가 하나도 없다.
여기서 다루는 건 "문진 눈금이 실제 반지하 분포와 맞는가" 뿐이다.

---

## 1. 신용카드 비교는 의미가 있나 — **있다. 다만 눈금이 틀린 자리에 있다**

### 실측 34가구가 말하는 것

현장조사 34가구의 현관 턱 실측값 분포:

| 실측 현관턱 | 가구 수 | 현행 enum 이 떨어뜨리는 칸 |
|---:|---:|---|
| 8.5cm (카드 1개) | 12 | `카드와비슷` → 9cm |
| 17.0cm (카드 2개) | 8 | `카드보다높음` → 15cm |
| 25.5cm (카드 3개) | 6 | `카드보다높음` → 15cm |
| 32.0cm (계단 2개) | 6 | `카드보다높음` → 15cm |
| 미확인 | 2 | — |

여기서 두 가지가 바로 보인다.

**① 아래 두 칸이 비어 있다.** `턱 없음`(0cm) **0가구**, `카드보다낮음`(5cm) **0가구**.
34가구 중 단 한 집도 카드보다 낮은 턱을 가지고 있지 않았다.
→ 4단계 중 2단계가 실측에서 한 번도 안 나온다. **눈금의 절반이 놀고 있다.**

**② 위 칸 하나가 17~32cm 를 전부 삼킨다.** `카드보다높음` 한 칸에 20가구(실측의 62%)가
몰리고, 전부 **15cm** 로 환산된다. 실제로는 17~32cm 인데 15cm 로 본다.

### 판정이 실제로 달라지는가 — 달라진다

32가구(방어높이 산출 가능)를 실측 cm / 현행 enum / 카드 개수 방식으로 각각 돌린 결과:

| 침수심 | 실측 cm | **현행 enum** | 카드 개수 방식 |
|---|---:|---:|---:|
| 9.3cm | 10/32 유입 | 10/32 | 10/32 |
| 15cm | 10/32 | 10/32 | 10/32 |
| **20cm** | **13/32** | **18/32** | **13/32** |
| 33cm | 18/32 | 18/32 | 18/32 |

**침수심 20cm 구간에서 현행 enum 이 5가구(16%)를 실제보다 위험하게 판정한다.**
카드 개수로 바꾸면 실측과 정확히 일치한다.

### 그래서 결론

카드 비교 자체는 **버리면 안 된다.** 거주자는 cm 를 모른다. 실물 척도가 필요하고,
현장조사자(김황현)도 지시 없이 독립적으로 카드를 기준으로 기록했다 — 척도 선택은 옳았다.

틀린 건 **비교 방식**이다.

| | 현행 | 제안 |
|---|---|---|
| 묻는 법 | 카드보다 **높냐 낮냐** | 카드 **몇 개냐** |
| 보기 | 없음 / 낮음 / 비슷 / 높음 | 없음 / 1개 / 2개 / 3개 이상 |
| cm 환산 | 0 / 5 / 9 / 15 | 0 / 8.5 / 17 / 25.5 |
| 실측 분포 | 2칸이 빔, 1칸에 62% 몰림 | 고르게 퍼짐 |
| 상한 | 15cm 에서 잘림 | 25.5cm |

**덤으로 풀리는 문제**: 김황현의 34가구 CSV 가 지금은 엔진에 그대로 못 들어간다
(그가 기록한 건 "카드 몇 개" 인데 enum 은 "높다/낮다" 라서). 카드 개수로 바꾸면
**매핑 없이 바로 들어간다.**

### 고칠 곳

```
functions/src/prompt.ts   SLOT_SPEC[0].options / enumValues
scripts/diagnose.py       SILL_CM          (차동현 소유 — 요청 필요)
src/utils/diagnose.ts     SILL_CM
functions/save.js         검증 enum 목록
```

⚠ 저장값 문자열이 바뀌므로 **이미 저장된 데이터가 있으면 마이그레이션이 필요하다.**
배포 전이면 지금이 바꿀 수 있는 마지막 타이밍이다.

### 창문도 같은 문제

`window_base` 는 `땅보다낮음(0) / 비슷(3) / 땅보다높음(20)` 3단계인데,
실측 창문하단은 8.5cm ×4 · 17cm ×12 · 25.5cm ×18 이다.
**`땅보다낮음` 도 0가구.** 전부 `땅보다높음` 한 칸에 들어가 20cm 로 환산된다.
현관과 같은 문제이고, 같은 방식(카드 개수)으로 고치면 된다.

## 2. 계단 개수는 중요한가 — **판정엔 안 쓴다. 그래도 물어야 한다**

### 지금 상태

`stair_count` 는 **경로 A 뺄셈에 들어가지 않는다.** 애초에 설계가 그렇다.
`STAIR_DEPTH_CM` 은 실내 바닥 깊이 추정과 경고 문구에만 쓴다.

이건 의도된 것이고 방어 논리도 명확하다 —
**계단 깊이는 "물이 들어오느냐"가 아니라 "들어온 뒤 얼마나 심각하냐"를 정한다.**
유입 여부는 개구부 높이가 정하고, 계단은 그 뒤의 이야기다.

### 그럼 왜 묻나 — 세 가지

**① 대피 안내가 달라진다.** 계단이 깊을수록 유입된 물이 고이고 빠지지 않는다.
현관문이 바깥으로 열리는 구조면 고인 물의 수압 때문에 문이 열리지 않게 된다.
`RAIN_GUIDE` 의 *"계단 물높이가 종아리(약 40cm)에 닿기 전에 나오십시오"* 가 이 항목에 걸려 있다.
반지하 침수에서 사람이 죽는 경로는 유입 그 자체가 아니라 **나가지 못하는 것**이다.

**② 우선순위가 달라진다.** `inflowCm` 이 같은 두 집이면, 계단이 깊은 쪽이 더 급하다.
공무원 콘솔에서 동률을 가르는 데 쓸 수 있다.

**③ 라벨 테이블 컬럼으로 남는다.** 나중에 실제 피해 기록이 붙었을 때 계단 깊이가
중요한 피처로 나올 수 있다. 지금 안 물으면 그 컬럼은 영영 비어 있다.
질문 하나(5초)의 비용으로 되돌릴 수 없는 데이터를 얻는다.

### 다만 고쳐야 할 것 두 가지

**(해소됨)** 현장조사에서 `계단 2개` 로 기록된 6가구가 현관턱 32cm 로 환산된 건
이 슬롯(`stair_count`)과 무관한 별개 기록이라고 류서현이 확인했다. 방향 문제 없음.

**⚠ 화면에서 역할을 분명히 해야 한다.** 지금은 다른 11개와 똑같은 모양으로 물어서
사용자가 "이게 내 판정에 들어가나 보다" 라고 오해한다. 결과 화면에서 이 항목은
**판정이 아니라 대피 안내** 쪽에 붙여야 한다.
