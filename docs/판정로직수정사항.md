# 판정 엔진 수정 요청 — 차동현

작성 2026-09-16 · 류서현 · 대상 `scripts/diagnose.py` · `src/utils/diagnose.ts` (두 파일 동일 로직)

엔진을 읽다가 두 가지를 찾았습니다. 하나는 판정이 **안전한 쪽으로 틀리는** 문제라 제출
전에 고쳐야 할 것 같고, 하나는 죽어 있는 분기입니다. 제가 담당 파일이 아니라 직접
수정하지 않았습니다. 수정 방향도 같이 적었으니 판단해 주세요.

---

## 1. 🔴 개구부 하나만 알아도 "방어가능" 이 나옵니다

### 지금 코드

`_diagnose_surface()` (diagnose.py 107행 부근 / diagnose.ts 동일 위치)

```python
known = [d for d in (entrance_def, window_def) if d is not None]
if not known:
    return {"status": "확인필요", ...}
effective = min(known)
```

**둘 다 모를 때만 `확인필요`이고, 하나만 알면 그 하나로 판정합니다.**

### 무엇이 문제인가

창문이 `땅보다높음`(20cm)이고 현관 턱이 `unknown` 인 집을 생각해 보겠습니다.
`known = [20]` 이므로 `effective = 20`, 침수심 15cm 면 결과는 **`방어가능`** 입니다.

그런데 확인하지 못한 그 현관 턱이 실제로 `없음`(0cm)이라면 그 집은 물이 그냥
들어옵니다. 실효 방어높이를 "가장 낮은 개구부"로 정의한 설계 자체는 옳은데,
**모르는 개구부를 계산에서 빼버리면 그 정의가 깨집니다.** 빠진 개구부가 바로
가장 낮은 곳일 수 있으니까요.

그리고 틀리는 방향이 **위험을 낮게 보는 쪽**입니다. 반지하 침수 서비스에서 이 방향의
오류는 반대 방향보다 훨씬 나쁩니다.

파일 머리말의 설계 원칙 4번 **"unknown 이면 추측하지 않고 판정 보류"** 와도 어긋나고,
`App.tsx` 에도 *"한쪽이라도 확인필요면 설비가 필요 없다고 말하지 않는다"* 는 주석이
달려 있는데 이 지점에서만 반대로 동작합니다.

### 수정 방향 (택일)

**A안 — 보수적. 하나라도 모르면 보류**

```python
if entrance_def is None or window_def is None:
    return {"status": "확인필요",
            "reason": "현관 턱과 창문 중 확인하지 못한 개구부가 있어 실효 방어높이를 정할 수 없습니다.",
            "effective_defense_cm": None, ...}
```

가장 단순하고 원칙에 맞습니다. 다만 `확인필요` 가 늘어납니다. 특히 김황현 현장조사
45가구는 골목 관찰이라 일부 unknown 이 섞일 텐데, 그 가구들이 전부 `확인필요` 로
빠지면 DS1 군집 표본이 줄어듭니다.

**B안 — 판정은 하되 불확실을 드러낸다**

알려진 것만으로 계산하되 결과에 플래그를 답니다.

```python
"effective_defense_cm": effective,
"unverified_openings": [이름 for 모르는 개구부],   # 새 필드
```

`유입가능` 은 그대로 두고(모르는 개구부가 더 낮으면 여전히 유입가능이므로 결론이
안 바뀝니다), **`방어가능` 인데 `unverified_openings` 가 비어 있지 않으면 화면에서
`확인필요` 로 낮춰** 보여줍니다. 판정 로직은 순수하게 두고 표시 단계에서 처리하는
방식이라 엔진 철학과 덜 충돌합니다.

저는 **B안**이 나아 보입니다. 표본 손실 없이 안전 방향을 지킬 수 있고, 화면 처리는
제가 `App.tsx` 에서 하면 됩니다. 어느 쪽이든 결정해 주시면 맞추겠습니다.

`scripts/test_diagnose.py` 에 이 경우 테스트가 없으니 같이 추가가 필요합니다.
예: 현관 unknown + 창문 `땅보다높음` + 침수심 15cm → 기대값.

## 2. 🟡 `build_year` 신호가 한 번도 발화하지 않습니다

### 지금 상태

`_diagnose_backflow()` 에 이런 분기가 있습니다.

```python
if build_year is not None and build_year < 1995:
    signals.append("1995년 이전 건축물로 배관 노후가 예상됩니다.")
```

그런데 `src/App.tsx` 386행의 호출이 이렇습니다.

```ts
return diagnose(slots, depth);      // 세 번째 인자 없음 → build_year 항상 null
```

**즉 이 신호는 서비스가 시작된 이래 한 번도 켜진 적이 없습니다.** 김황현 현장조사
지시서에도 건축연도 항목이 없어서 앞으로도 채워지지 않습니다.

경로 B 상태는 신호 개수로 갈리기 때문에(`>=3` 이면 매우미흡, `>=1` 이면 미흡)
이 신호가 빠진 만큼 역류 위험이 **실제보다 낮게** 나오고 있습니다.

### 선택지

1. **건축연도를 실제로 채운다.** 주소가 있으면 국토교통부 건축물대장 API 로
   사용승인일을 조회할 수 있습니다. 사용자에게 묻지 않아도 되고 정확합니다.
   다만 API 키 발급과 연동 작업이 붙습니다 — 마감을 생각하면 이번엔 무리로 보입니다.
2. **슬롯로 추가한다.** 거주자가 건축연도를 아는 경우가 드물어 unknown 이 많을 겁니다.
3. **코드에서 빼고 문서에 남긴다.** "배관 노후는 역류의 알려진 요인이나 이번 범위에서는
   수집하지 않았다" 로 한계에 명시합니다.

마감까지 5일이라 **3번**을 제안합니다. 코드에 있는데 돌지 않는 상태가 제일 나쁩니다 —
심사에서 코드를 보면 바로 걸립니다. 1번은 제출 이후 과제로 남기면 좋겠습니다.

## 3. 참고 — 가중 요인이 판정에 안 들어가는 것에 대해

`_collect_warnings()` 의 여섯 항목(창문 하단, 차양, 골목 경사, 빗물받이, 계단 깊이)이
경고 문구로만 나오고 판정에는 영향을 주지 않습니다. 이건 **임의 배점표를 만들지 않겠다는
설계 의도**로 이해했고, 저는 동의합니다.

다만 심사에서 *"그럼 왜 물어보나요"* 가 나올 수 있습니다. 답을 미리 맞춰두면 좋겠습니다.
제 생각은 이렇습니다.

> 이 요인들은 침수 확률을 높이지만, 얼마나 높이는지를 정량화하려면 하수관망 해석이
> 필요합니다. 근거 없는 가중치를 곱하는 대신 판정과 분리해 경고로 제시하고, 사용자가
> 조치할 수 있는 항목(빗물받이 신고 등)은 행동요령으로 연결했습니다.

특히 `stair_count` 는 계단이 깊을수록 유입 후 배수가 어려워 피해가 커지는데, 이건
**유입 여부**가 아니라 **유입 후 심각도**라서 경로 A 뺄셈에 넣지 않은 게 맞다고 봅니다.
이 구분을 발표에서 설명하면 오히려 설계가 정교해 보일 것 같습니다.

## 4. 같이 알아두면 좋은 것 — 방어높이 조합은 48가지뿐입니다

`tools/defense_lattice.py` 를 만들어 두었습니다. `scripts/diagnose.py` 를 그대로
import 해서 쓰므로 엔진을 고치면 분석도 자동으로 따라갑니다. 지금 돌린 결과입니다.

| 실효 방어높이 | 조합 수 | 누적 |
|---:|---:|---:|
| 0cm | 13 | 27.1% |
| 3cm | 7 | 41.7% |
| 5cm | 4 | 50.0% |
| 9cm | 4 | 58.3% |
| 15cm | 4 | 66.7% |
| 20cm | 4 | 75.0% |
| 30cm | 6 | 87.5% |
| 33cm 이상 | 6 | 100% |

**판정이 뒤집히는 문턱은 이 11개 값뿐입니다.** 침수심을 20cm 로 잡든 25cm 로 잡든
결과가 같고, 21cm 를 넘는 순간 66.7% → 75.0% 로 튑니다. 도시침수지도 등급 → cm
환산값(`SEG_DEPTH_CM`)이 아직 확정되지 않았는데, 이 표가 있으면 **그 값이 어디로
정해지든 결론이 얼마나 바뀌는지**를 미리 말할 수 있습니다.

그리고 방어높이 0cm 조합 13개 중 6개가 `현관 턱 없음 + 물막이판 미설치` 입니다.
현관이 뚫려 있으면 창문을 아무리 높여도 실효 방어높이는 0입니다. **현관 물막이판이
단일 설비로는 효과가 가장 큰데 안양시 미지원 품목**이라는 게 정책 제언으로 바로
쓸 수 있는 결과로 보입니다.

45가구 CSV 가 들어오면 같은 스크립트가 조합별 실제 빈도로 가중해 다시 계산합니다.
그때 나오는 문장이 사업계획서에 쓸 형태입니다.

> 안양 실측 침수심 9.3~33.0cm 구간에서 조사 45가구 중 N~M가구가 지표 유입 가능

두 축(침수심·방어높이)이 모두 안양시 실측이라 도시침수지도 등급 환산값에 의존하지
않습니다. 확정 못 한 숫자를 확정한 척하지 않아도 되는 구조입니다.
